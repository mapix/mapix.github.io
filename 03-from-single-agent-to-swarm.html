多 Agent 协作演进：从单兵到 Swarm

多 Agent 协同并不只是找几个分身一起打字。沿着实际写代码时踩过的坑走一遍，你会发现每一次多请一个角色进场，都只是为了解开上一层刚刚卡死的那个结。

#03

过去大半年，身边的工程师聊起 AI 编程，话题悄悄变了。

去年大家还在比谁家的单模型一次能吐出几千行代码、谁的推理分高；到了今年，聊得最多的词变成了 Subagent、Swarm、Agent Teams。很多人的第一反应是：哦，无非是多开几个窗口并发干活，打字速度翻几倍。

其实只要你真的陪着一个编程 Agent 连续改过两小时代码，就知道瓶颈很少出在“打字不够快”上。真正让它卡住的，往往是两个非常像人的毛病。

第一个毛病是脑子被碎纸片埋住了。它翻过的三十个文件、终端吐出的四百行报错、试错时写废的脚本，全堆在同一个上下文窗口里。聊到第十轮，它早就忘了你第一句话叮嘱过“别动老接口的返回值”。

第二个毛病更隐蔽：自己写完的作业，自己舍不得打低分。写代码和写测试用的是同一个上下文，带着一模一样的偏见，改着改着，模型甚至会顺手把一条棘手的断言改弱，只为了笑着告诉你“测试全部通过了”。

前两天我顺着 Google Antigravity 2026 年的几次大版本迭代一路捋下来，发现它的演进路线很克制，也挺反直觉：并没有一上来就搞平级群聊，而是顺着 Single Agent → Subagents → /boost → /teamwork → /swarm 五级台阶，每撞一次真实的天花板，才多请一个角色进场——先用严格的层级与制度镇住大工程，最后才把金字塔拍平成共享黑板。

单 Agent 很好用，直到它的桌子被埋住

一切的起点，都是你每天最熟悉的那个单兵窗口：一个 Primary Agent。

它骨子里跑着一个极朴素的循环：先想一步（Thought），接着调工具读文件、改代码或跑测试（Tool Call），再把返回的结果原封不动塞回自己的对话记录（Observation），然后接着往下想。

如果只是写个数据清洗脚本，或者修一个行号明明白白的报错，这种单兵作战几乎是无敌的——没有沟通损耗，几十秒就收工。可只要你让它跨过五六个文件改状态机，下面这台时间线播放器里的画面就会很快出现。

你看，它并不是突然变笨了，只是像一个老厨师，既要掌勺盯火候，又要自己跑去门口收快递、剥蒜、洗碗，最后案板上堆满了烂菜叶，连客人在外面点了什么菜都忘了。

所以解决的办法也很直觉：大厨别亲自去洗菜了，门外找几个临时工，干完活只把洗好的菜递进来就行。这就是 Antigravity 迈出的第一步：Subagents。

Subagents：先学会把满手灰的活外包出去

Subagent 说白了就是主 Agent 通过 invoke_subagent 临时喊来的短工。它的妙处在于自带一张空白桌子——在自己沙盒里翻五十个文件、踩十个坑，全都不占主 Agent 的脑子；干完之后，只往回递一张折好的结论小纸条，然后就地解散。

Antigravity 并没有一次塞给你一堆工种，而是顺着主 Agent 平常最常被弄脏的三个场景，逐个配齐了三个内置帮手。

先解决翻代码：research

以前主 Agent 改一个老接口前，得先用 grep 把全库里调用它的地方全搜出来看一遍，光这一步就能吃掉小半个上下文窗口。其实“找线索”这件事根本不需要改文件，主 Agent 真正想要的只是“究竟哪几个文件调了它”。

再解决点网页：browser

源码读懂了、代码也编译过了，但写前端和全栈的人都知道，页面上点下去到底报不报错，光看源码是猜不出来的。可如果把整个浏览器的 DOM 树、截图和几十条 Console 日志直接倒进主对话，主窗口照样立刻喘不过气。

遇到想并行写代码的时刻：self

前面两位都只看不写。可有时候我们想同时试两种不同的重构路线，或者有两个互不相干的模块想一起动工，这时候只读帮手就帮不上忙了；可如果让两个能写代码的 Agent 共用同一个目录，一转眼就会互相覆盖。

看看这组对比：同样是“搜库 + 测浏览器”，把 research 和 browser 放出去，主窗口水位几乎纹丝不动；硬塞进同一个窗口，立刻就会红灯报警。

靠着这几位帮手，日常开发其实已经很舒服了。直到有一天，我撞上了一个只在特定并发时序下才偶发的死锁 Bug。

连着让它修了两轮、甚至也派了 research 去搜代码，问题还是时好时坏。盯了几轮执行记录后我才看明白原因：Subagent 更像是跑腿的临时工，主 Agent 自己一看到报错就手痒，还没把调用链查穿就急着改一行试试；改完一测没过，又带着愧疚感继续打补丁，把案发现场弄得面目全非。

对付这种深水 Bug，要的不是找人帮忙翻书，而是得把“查案”和“动刀”强行隔开。这就是 /boost 上场的时刻。

/boost：先请法医锁死案情，再让主刀医生上台

在 Antigravity 里输入 /boost，相当于按需拉起一套三层深思流水线。它不急着把代码改出来，而是先把三件事分别交到三类互不越权的角色手里。

先按住急着写代码的手：Orchestrator

平时写着写着跑偏，往往是因为“定计划的人”和“敲代码的人”是同一颗脑子，一钻进某段报错的细节里，就忘了全局还差哪几条边界没验。所以 /boost 的第一件事，是在最顶层放一个全程不碰业务代码的总调度。

把写权限收走：DeepInvestigator

接着是最关键的一步。人也好、模型也好，只要手里握着编辑器，看到诡异报错就总想“先改一行打印看看”——结果经常把本来还能复现的现场改散了。要治这个毛病，最管用的办法就是请一个没有写入权限的侦探。

拿着证据上手术台：DeepCoder 与独立测试沙盒

案情水落石出之后，才轮到真正动手改代码的人出场，改完还得交给一个不认识作者的独立沙盒去验货。

把这三层闭环拆开走一遍——留意第 4 步压测没过时，它是怎么带着报错堆栈打回顶层重修的：

把 /boost 比作一台往地下深钻的钻井机很贴切——对付单点深水难题非常趁手。可一旦走出单个 Bug，把视野拉到跨好几天的整库重构、老框架迁移，或者高难度仿真工程上，光靠一口井就远远不够了。

多天长跑最先暴露的是两个硬伤：一是开头如果没把“究竟要做成什么样”聊透，跑了一天半才发现方向偏了；而且连续干上几天后，连总控自己的上下文都会变得粘稠疲劳。二是任务一难、时间一长，模型甚至可能动起“写个假测试糊弄过去”的歪脑筋。

大工程靠的从来不是临场发挥，而是制度。这也是为什么早在 2026 年中、比后来的 Swarm 更早几个月，Antigravity 就先推出了这套纵向的重装体系：/teamwork。

/teamwork：先立规矩再开工，跨天工程的正规军

比起随叫随到的临时协作，/teamwork 更像一支真正拉出来打硬仗的正规工程团队。它把过去人类公司里用血泪换来的几条规矩，一条一条写进了智能体的运行流程里。

动工前的十分钟：需求面试官（Scoping Interview）

大项目最怕“还没想清楚就开始写代码”。所以 /teamwork 上来不会立刻建文件，而是先拉着你做一轮结构化访谈，遵循一句老话：Specify what, not how（说清要什么，别瞎指挥怎么写）。

跑到第五天依然清醒：里程碑接力（Milestone Handoff）

不管上下文窗口标称有多大，同一个总控跑上几千步之后，注意力一定会变钝。/teamwork 对付上下文衰老的办法相当干脆：既然一个人跑久了会累，那就别让他跑到底。

交付前的最后三道关：把验收权拆成三权分立

到了跨天大项目里，光靠一个测试沙盒远远看不住死角——代码能不能长期维护、极端并发抗不抗得住、有没有人在偷偷写假测试？/teamwork 干脆把验收拆给了三位性格迥异的审查官。

用过几回 /teamwork 之后，你会发现它确实能把跨周大迁移管得稳稳当当。可反过来看，它的毛病也很明显——太沉了。

如果今天下午你只是想快速做完一个常规新功能：后端接口、前端页面、集成测试本来可以三路齐头并进，写完一个字段想随手喊一声“我提交了，帮我跑下测试”，难道每次都要先开面试签契约、再一棒一棒按里程碑往上层汇报吗？

而且回头仔细一想，无论是 Subagents、/boost 还是 /teamwork，本质上都还是金字塔式的纵向汇报——工人之间没法直接对话。于是到了 2026 年 11 月，Antigravity 干脆把金字塔拍平，往工坊正中间搬出了一块大家都能看见的公共黑板：这就是最新一代的 /swarm。

/swarm：把金字塔拍平，搬出一块公共黑板

输入 /swarm 的那一刻，你所在的对话就变成了一间热闹但井井有条的工坊。为了让多个人同时动工不打架、还不至于在群里无意义刷屏烧光额度，Swarm 依次立起了四个角色。

先把包工头的手按住：Coordinator

很多人自己试着拉几个 Agent 并行干活时，最容易犯的错就是：一边给别人派活，主窗口自己也顺手去改某个文件。结果写代码写得太投入，旁边有个 Agent 问了一句“接口返回格式是什么”，半天没人理，整场协作静悄悄地凉在那里。

按工种命名、靠门铃叫醒的：Workers + 共享白板

早先的 Subagent 彼此之间像隔着墙，@ui 想问 @api 一句话，必须绕道主 Agent 当传话筒。而在 Swarm 里，所有工人共同盯着同一块按 #1、#2 顺序往上贴条的共享消息板（Board）。

只挑刺、绝不越界替人改的：对抗式 Verifier

工人们自己写完代码，自然总觉得差不多能用了；可如果让检查者顺手去帮作者改 Bug，两个人又会撞进同一个文件里把现场写乱。

怕整群安静下来没人管的：Monitor

既然平时大家都在睡眠等门铃，万一某个工人发完消息忘了顺手 @ 下家，整个群就会突然陷入一种滑稽的冷场——每个人都在等别人先开口，谁也没注意到活还没完。

四个角色站齐之后，整场配合看下来就很有意思了。你可以一步步点“下一步”，看看一条 #1 到 #5 的消息流是怎么把大家按需叫醒的（在 Antigravity App 的 Swarm 面板里，也能用 Board / Members / Graph 三个视图直接围观这个过程）：

一张表看懂差异，以及平时怎么挑

走到这一步再回头看，五种模式并不是层层覆盖、越往后越高级的替代关系。改个小样式也把 /teamwork 搬出来，不仅慢，纯属杀鸡用牛刀；反过来让单 Agent 硬扛整库迁移，大概率两小时后就开始在原地兜圈。

协作模式 请出的关键角色 怎么沟通 帮你避开了什么坑 别拿它干什么
Single Agent Primary Agent 单线程 ReAct 循环 零沟通成本，快到飞起 别硬扛跨多文件、长日志的重活
Subagents research / browser / self 星型单线，只对父节点交差 把搜库、点网页的噪声挡在主窗口外 别指望它硬解需要反复推理交锋的深水 Bug
/boost Orchestrator · DeepInvestigator · DeepCoder 垂直三层（调度 → 查写分离 → 验收） 改掉了“边猜边改”和自己改弱测试的毛病 别用来做大量本来就能并行的普通页面
/teamwork Milestone Orch · Critic · Challenger · Auditor 纵向立项契约 + 换棒接力 + 三道验收门 防住长周期健忘、走偏方向和写假测试 日常小修小补就别摆这套重装阵仗了
/swarm Coordinator · Workers · Verifier · Monitor 拍平层级，改用共享黑板 + @mention 门铃 多模块并发推进，发现问题点对点打回 别动不动就 @all，不然全员一起烧额度

回头看过去这一年的变化，觉得挺有意思的。

如果说我们在前两篇聊过的“微雕刻”和“立标尺”，还更多是在讲人与 AI 一对一打交道时的手艺；那么到了多智能体这一层，AI 几乎是在用几个月的时间，把人类软件工程花几十年攒下来的组织演进重新走了一遍——从单兵手工作坊，到外包打前站，到法医与主刀分开的专案组，到先签契约、换棒接力、三道门神守关的正规军（/teamwork），再到最后把金字塔拍平、靠共享黑板和 @mention 门铃点对点协同的敏捷工坊（/swarm）。

往后真正拉开差距的，恐怕不再是大家手里用的模型参数差了几个百分点，而是遇到棘手问题时，你一眼就能看清：此刻卡住我们的到底是桌子被弄乱了、查和写搅在一起、周期太长容易跑偏，还是多路推进没铺开——然后顺手替它选对了那张刚好合身的协作阵型。
