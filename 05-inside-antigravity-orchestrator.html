同会话双模交接：拆解 Antigravity Orchestrator

单模型跑到底太烧额度，按请求硬切的 Model Router 脆而不可控，按 Subagent 切模型又隔着一层有损摘要。Antigravity Orchestrator 的做法是保留同一条会话轨迹，在宿主 Harness 层用三态状态机、显式计划与工具门禁，让高推理规划模型和轻量执行模型在同一个现场接力。

一段几十步的单会话编码任务，算力需求分布极不均匀：开头理清依赖、敲定接口，以及收尾核查边界，需要重推理模型；中间占大头的改文件、修局部类型错误、跑单测，主要吃响应速度。

把快慢模型配合起来用，常见有三条老路，各有明显短板：

  1. 单模型单 Session 一条道走到黑。上下文完整，Prompt Cache 也能一路命中，但没有算力区分。全程挂 Gemini 4 Carbon 每次调工具都要等长推理，前沿额度消耗极快；全程挂轻量模型写常规代码很快，遇到跨多文件的状态耦合则容易反复试错打转。
  2. 请求级 Model Router。要么根据首句 Prompt 猜难度锁死模型，要么在网关层按长度、关键字逐请求切换。问题在于编码任务的真实复杂度往往写到中途才暴露；外部路由器看不出当前处在排查、改码还是验收阶段，硬切会打断推理链与签名状态（Thought Signatures）。既没有交接契约也没有工具限制，小模型改偏了没有通道退回大模型，来回跳模型还会把双边的缓存前缀打碎。
  3. 以 Subagent（或独立多 Agent）为边界切模型。任务天然解耦时这条路很顺——例如官方博客展示的 Antigravity SDK 仓库分流：前置一群 Gemini 4 Hydrogen Agent 处理高频 Issue 分流、代码检索、追问提单者和简单 PR 修改，独立的 Carbon Agent 负责跨模块重构与安全审查。但放回紧耦合的单次编码会话，模型边界被迫绑在上下文边界上：子会话看不到主会话前面读过的原始源码，主会话看不到子会话改码中途踩过的真实报错，靠摘要传话一旦撞上设计冲突，同步损耗很大。

Antigravity 的 Orchestrator 给出了第四种方案：不拆子会话，也不按单次请求盲切，而是在同一条持久化轨迹（Trajectory）和工作区上，固定配对高推理规划模型（Carbon 或 Argon）与高速蒸馏执行模型（Hydrogen），由宿主 Harness 在粗粒度的阶段边界调度切换。

前提与职责切分：执行端够稳，控制权归 Harness

早年同会话双模很难跑通，卡在轻量模型的多步工具调用和精确编辑太脆，接手几步改乱现场，规划模型反复救火反而更慢。

同步发布的 Gemini 4 Hydrogen 先补上了执行底座：官方基准中，它在 Artificial Analysis Intelligence Index 拿到 51 分（开 xhigh 档达 54 分），Terminal-Bench 4.1 单跑达到 57%（前代 3.8 Flash 为 18.2%）。直选 Hydrogen 时开放 low、medium、high、xhigh 四档思考深度；进入 Orchestrator 后则锁定为固定配对（Carbon + Hydrogen 或 Argon + Hydrogen），不再开放 /effort 微调，以此换取稳定的能力预期。

系统在运行时把职责切开：会话轨迹与本地工作区归宿主 Harness 持久化，不属于任一模型的私有状态。每次调用模型前，Harness 根据当前阶段替换模型 ID、系统提示词和可用工具列表；模型返回工具调用后，真正落盘前还要经过前置 Tool Gate 做权限拦截。模型只能调用交接工具提议切换，状态翻转和换模完全由 Harness 执行。

这也划清了它与 Subagents、/swarm 的边界：后两者拆开多个独立上下文和 Git worktree 做空间并行；Orchestrator 留在单个 Agent 实例内做阶段算力调度。

三态状态机与显式交接

Orchestrator 的双向切换围绕 Planning、Executing、ReviewPending 三个状态运转，正常流转走工具协议，异常与防漂移走 Harness 硬钩子：

  • 去程（Planning → Executing）：空闲态收到用户请求一律先进 Planning，运行 Carbon 或 Argon。Tool Gate 封禁写操作，只放行读文件、搜索及编译测试等只读观察命令。纯提问或代码评审直接回复收工，全程不调 Hydrogen；需要改工作区时，规划模型必须调用 exit_plan_mode 提交完整计划，Harness 随后切入 Executing、换上 Hydrogen 并解开写权限。
  • 为什么共享了完整历史还要写显式计划？ Hydrogen 能看到前序所有文件读取与工具输出，但看不到 Carbon 内部推理（Thinking）里排除备选方案的过程。只丢几万 Token 原始检索流水，等于让轻量模型重做一遍全局归纳。因此 exit_plan_mode 的计划必须写明目标文件与函数符号、修改顺序、验证命令及预期输出，外加当前任务的 Re-plan if 清单。
  • 回程一：执行端按协议熔断（Executing → Planning）：补漏掉的 import、微调路径、重跑一次偶发抖动的单测，由 Hydrogen 自行消化；一旦撞上四类边界——同一验证连续两次失败、代码现状与计划前提冲突、出现未拍板的设计分叉、需修改计划外文件——必须停手调 enter_plan_mode 退回规划态。
  • 回程二：Harness 硬门禁强拦（ReviewPending）：防止快模型失控硬冲，Harness 外挂了两条确定性 Review Hook。一旦命中，状态立即置为 ReviewPending，Tool Gate 锁死除 enter_plan_mode 外的一切工具，逼 Hydrogen 汇总现状交棒：
    1. 执行期用户插话：Hydrogen 连续调工具途中用户发来新消息，禁止执行模型临场改方案，强制退回 Carbon 统一重排计划。
    2. 满 30 次模型响应定频复核：逆向扫描上次交接、复核或已完成用户输入以来的轨迹，执行模型每累计产出 30 次模型响应强制触发一次。注意计数单位是模型响应步数——单轮并发读 8 个文件算 1 步，等待 10 分钟构建算 0 步。

切回 Planning 后，Carbon 借只读工具查验真实 diff 与测试输出：达标则交付；属 30 步常规体检且方向正确则下发剩余步骤；跑偏则在修订计划里指明回滚范围与新改法。

Prompt Cache 账本：冷启动付在哪，缓存怎么保住

异构模型权重不同，底层 KV Cache 无法跨模共享；服务端隐式 Prompt Cache 按模型各自建池、按前缀独立匹配。下面是一次 Carbon → Hydrogen → Carbon 往返任务（建文件、断言验证、回程复核）的 7 轮实测 Usage 账本：

Carbon → Hydrogen → Carbon 往返 7 轮 Token 实测数据
轮次 执棒模型 普通输入 (inputTokens) 缓存读取 (cacheReadTokens) 总输入 命中率 缓存状态
#1 Gemini 4 Carbon 11,313 0 11,313 0.0% Planner 首次冷启动
#2 Gemini 4 Carbon 2,335 9,259 11,594 79.9% Planner 暖命中
#3 Gemini 4 Hydrogen 12,566 0 12,566 0.0% 切入 Executor，冷启动预热
#4 Gemini 4 Hydrogen 2,389 10,517 12,906 81.5% Executor 暖命中
#5 Gemini 4 Hydrogen 2,121 10,951 13,072 83.8% Executor 暖命中
#6 Gemini 4 Carbon 2,714 11,595 14,309 81.0% 切回 Planner，旧缓存仍命中
#7 Gemini 4 Carbon 2,691 12,260 14,951 82.0% Planner 持续暖命中

7 轮累计总输入 90,711 Token，缓存读取 54,582 Token（总复用率 60.2%；剔除 #1、#3 两次冷启动后，5 次暖调用平均命中 81.7%）。账本里有两个关键事实：

  1. 牺牲的是第二模型进场的首轮预热，切回时原模型缓存不丢。#3 切给 Hydrogen 付了 12,566 全价输入预热，随后在 #4、#5 连续吃满 80%+ 缓存；#6 交回 Carbon 时直接读出 11,595 缓存 Token（81.0%），只为 Hydrogen 施工期新增的增量付费。只要往返未超服务端缓存 TTL，且 Carbon 头部的 System Prompt、Tool Schema 与早期前缀保持稳定，原缓存依然有效。对比逐请求横跳的网关 Router，阶段级切换把预热次数压到最低，让执行模型在长施工段里充分摊薄冷启动成本。
  2. 暖调用里固定的两千多普通输入来自 2,050 Token 尾窗规则。Gemini 4 隐式缓存（满 4,096 Token 自动生效）只有在单轮新增内容达到 2,050 Token 时才将上一轮完整封入缓存；增量不足 2,050 Token 时，上一轮末尾的 2,050 Token 会按普通输入重算。拿 #6 → #7 验算：总输入从 14,309 增至 14,951，增量 642 < 2,050，理论 cacheRead = 14,309 - 2,050 = 12,259、理论 input = 642 + 2,050 = 2,692，与实测 12,260 / 2,691 仅差 1 个分词边界 Token。

成本算式与三条边界

以全程强模型基线成本为 1，设可由执行模型接管的施工占比为 f，执行模型相对强模型的综合单价折扣比为 r（r < 1），写计划、二次冷启动、复核与返工带来的额外固定开销占比为 h，则相对成本为：

C_rel ≈ 1 − f × (1 − r) + h
满足 f × (1 − r) > h 才有净收益。

官方披露的 Terminal-Bench 4.1 实测——成功率接近全程 Carbon，平均省 24% quota、快 19%——正好落在 f 较高且一两次交接即收敛的区间。落到实际工程里要注意三条边界：

  • 两头场景会倒贴：两三步改完的琐碎修改 f 太小，写计划与 Hydrogen 冷启动开销 h 超过模型差价，直接单选 Hydrogen 更省；需求与实现强耦合、改两行就推翻假设的探索任务会频繁触发 enter_plan_mode 往返，直接单跑 Carbon 更稳。
  • 不突破单线串行耗时：同一时刻主轨迹只有一个模型在跑，前后端与测试能拆开并发的工程仍需交给 Subagents 或 /swarm。
  • 同源上下文锚定：两模型共用同一条轨迹，Carbon 最初漏掉的边界条件若单测也没覆盖，回程复核时很容易顺着自己列的清单放行。双模接力替代不了客观验证脚本和独立测试审校。

自研落地要点与选型对照

在自研 Coding Agent Harness 中复现这套机制，靠 Prompt 扮演角色没有意义，运行时至少需要落齐五件事：

  1. 阶段与计划原子持久化：落盘维护 PLANNING / EXECUTING / REVIEW_PENDING / DONE 与生效计划，防止中断重启后丢失阶段或重复执行副作用。
  2. 追加式原始轨迹 + 阶段水位线：完整保留工具调用与返回原文，不压成有损摘要；在交接与复核处写入边界标记供步数扫描。
  3. 跨模请求装配与签名隔离：换模（尤其跨厂商模型配对）时剥离或转换历史中的 thinking / signature 字段避免校验报错，同时固定各模型头部的 System Prompt 与 Tool Schema 顺序以保住前缀缓存。
  4. 成对注册交接工具 + 前置 Tool Gate：规划态挂 exit_plan_mode 并拒掉写操作；执行态务必挂上 enter_plan_mode（漏注册会导致遇阻报 unknown tool 卡死）；ReviewPending 态拒掉除交回报告外的一切工具。
  5. 按风险信号提前拉起复核：除最高优拦截用户插话和 30 步保底外，可在检测到改动公共接口、触碰计划外文件或连续报错时提前切入 ReviewPending。
