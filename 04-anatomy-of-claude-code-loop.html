拆解 Claude Code 的 Loop

每个写过 Agent 的人都写过那二十行 while。但在真实仓库里连跑几小时之后，这套循环会在第 15 秒、第 20 分钟、第 1 小时和第 2 小时接连露馅。Claude Code 今天这套复杂内核，就是被这四次崩塌一步步逼出来的。

写一个能干活的 Agent 原型，核心只需要二十行 while：把对话发给模型，模型说要调工具就在本地执行，把结果塞回消息末尾再问一遍，直到模型不再调用工具为止。

用它修一个行号明明白白的报错，快得像一阵风。可如果你真的想让它独自进驻一个大仓库，连续改上几十分钟、甚至隔着几小时盯完一次发布，这二十行循环会立刻变成事故现场。问题不是一次性全砸过来的，而是随着任务时间越拉越长，顺着四个时间尺度一层一层露出来的。

二十行循环的蜜月期，在真实工程里活不过一小时

最初的设计朴素得像教科书：人类敲回车、模型推演、工具执行、结果回填，一条单行道走到黑。但在真实终端里连续跑起来之后，四幕诡异的故障会准点找上门：

  1. 第 15 秒就报错中断。模型为了提速一次并发读三个文件，其中两个还没返回，后台一个子任务恰好跑完插进来一条通知。下一秒接口直接拒绝请求，因为对话顺序被撕裂了。
  2. 第 20 分钟突然变慢、账单翻倍。聊过二十几轮后，逻辑一点没变，响应却从两秒拖到二十秒，甚至前面刚约定好的修改约束也被抛在脑后。底层几万 Token 的 Prompt Cache 莫名其妙全盘作废了。
  3. 第 1 小时卡死或被插件劫持。个人装的插件、公司下发的合规策略和内置功能挤在同一个进程里。一个写坏的扩展超时直接拖死主线，而对话撞上上下文窗口红线时，屏幕僵在那里干等几十秒生成摘要。
  4. 第 2 小时发现它原地“偷懒”停机。前面三关全扛过去，结果模型改完代码随手回了一句“看起来没问题了”，循环咔哒一声停住。测试还没跑绿、灰度发布才推了 10%，它却退回原点等人类来敲下一次回车。

Claude Code 并没有在二十行 while 里越塞越多 if-else。每次撞穿一个时间尺度，它就在外面加筑一道新防线。先用下面这张演进地图看清全貌，再沿四个故障现场一步步往深处拆：

第 15 秒：并发与插话把消息链撕裂，先学会做“短事务”

最先出事的地方在单次回合（Turn）内部。

大模型 API 协议在消息顺序上有近乎洁癖的硬约束：模型吐出的每一个工具调用块，紧接着的下一条内容里必须严丝合缝跟着对应编号的结果块。只要中间夹进任何别的东西，哪怕只是插件顺手插了一句状态提示，整条请求都会被当场打回。

更棘手的是多路来源混杂。驱动现代终端循环的早就不只人类键盘，后台子任务完成回调、定时触发器、手机端遥控指令、插件注入的上下文，全都要挤进同一扇门。如果全当成普通消息往数组末尾硬塞，不仅会撕裂调用链，还可能出现极端漏洞：外部代码仓库里一段恶意文本或后台提醒，混进人类输入通道后直接伪装成人工指令绕过权限审批。

出身锁死与安全汇入点

任何输入跨进内核边界时，引擎都会强制写入一条只读的来源属性，外层扩展只能查看、绝对改不了，机器触发的通知永远冒充不了人工键盘。要是上一轮还在等模型或跑工具，新消息不会半路腰斩当前执行，而是带着回合编号进队列排队，严格等到本轮彻底收尾，或者下一轮请求发出前的安全间隙才准汇入。

服务端直跑与五级权限漏斗

模型进入流式推理后，并不是所有工具调用都会回到本地执行。像内置顾问这类纯推理辅助工具，由模型 API 服务端直接运行并当场把结果缝进同一步输出里，压根不穿过本地沙盒。

真正落在本地的工具调用，会依次经过一道五级递进的权限漏斗：

  • 前置拦截层。允许扩展在执行前重写参数、直接短路返回或登记追踪，用于识别还没过审批就试图抢跑的行为。
  • 用户规则钩子。运行项目或用户自定义的前置检查脚本。
  • 声明式策略裁决。结合静态允许列表、当前权限模式和组织策略上限，算出放行、询问或拒绝三种静态结论。
  • 动态裁决与审批兜底。落入询问分支时，自动模式下交给安全分类器判断，常规模式下暂停等待人工确认；即便被拒，也保留了一次钩子重试的机会。
  • 不可重入执行口。权限落定后的最后一道物理闸门，确保同一个工具调用标识绝对只执行一次，任何重复触发都会在内核层被直接拒绝。

Fork-Join 屏障与消息配对原子性

单步推理经常同时派发三五个工具调用。为了吞吐量，工具本身和工具完成后的单个通知可以并发执行，但引擎在循环折返处立了一道 Fork-Join 批次屏障：必须等这一步里的所有工具全部落定，才统一进入批次汇总，再发起下一次模型请求。

第 20 分钟：过二十轮就慢成蜗牛，把 Prompt Cache 当成 CPU 缓存来管

单回合不再报错之后，开发团队很快撞上了第二堵墙：多轮复杂改造只要超过二十轮，延迟和成本就开始指数级恶化，甚至模型还会突然忘记前面定好的修改约束。

真相藏在 Prompt Caching 的工作方式里。和直觉里的键值对缓存不同，大模型上下文缓存遵循极其苛刻的字节级前缀匹配。它像一条只能从左往右核对的长磁带，从头到尾只要中间改动哪怕一个标点符号，断点之后积累的几万 Token 缓存瞬间全部作废，连带着前面算好的思考链上下文也要被迫丢弃重算。

最初的循环写法对此毫无防备。往系统提示词开头拼一个动态时间戳、进入深层目录顺手加载局部规则，或者中途新连上一个外部工具直接塞进列表，在短测试里风平浪静，放在二十分钟的长修改里就等于每过几轮亲手把缓存砸烂一次。更隐蔽的是，后台凭证每小时刷新、或者账号额度在恢复会话时切换，哪怕只重排了一下工具序列化顺序，长跑会话就会准点“失忆”。

Claude Code 干脆把 Prompt Cache 当成 CPU 的 L1/L2 缓存 来做硬隔离，用牺牲一点热插拔即时性，换取长会话稳定 90% 以上的缓存命中率：

  • 宁可放弃微调，也要死守前缀分段墙。系统提示词被硬切分成“跨会话全局共享静态区”和“当前会话固定区”，并强行规定全局静态段排在前面、交界处打下缓存锚点。一旦外层扩展试图插队把静态顺序弄乱，内核直接丢弃该修改。
  • 在线程生命周期内冻结工具池。只要会话还在同一条线程里继续，哪怕中途挂上新外部工具或插件改写描述，默认全部冻结不进前缀，一直憋到下一次上下文压缩、清空或开启新会话时才放行切换。大量外部工具则通过延迟加载标记收进按需搜索后面，防止开场就把前缀撑爆。
  • 把一切变化全赶到消息流最尾巴。当前时间、工作模式切换提示、深层目录回溯发现的局部规则文件，一律禁止碰前面三个静态缓存段，全部做成独立附件单向追写到消息末尾。

第 1 小时：插件抢权与窗口撞线，套上零信任洋葱和“54 分钟偷跑压缩”

当循环既能并发又不轻易击穿缓存之后，运行时间拉长到小时级，两类更深层的矛盾冒了出来。

第一类来自生态共处。开发者自己装社区插件，企业 IT 强推合规基线，产品自身还要跑内置功能。如果把三拨人挂在同一个平级 Hook 数组里按顺序执行，后加载的社区插件随时能把安全防线盖掉；一个写坏的扩展超时，更是直接拖垮整条开发主线。

五层洋葱“夹心”与冷酷的故障分界

Claude Code 把循环动作全收编进一条零信任洋葱链，从外向内依次穿过：

组织前置 → 用户扩展 → 组织后置 → 内置能力 → 引擎内核
  • 把不可信插件夹在中间。组织策略守住外层入口与内层兜底，遇到安全基线、上下文压缩和工具校验底线时，外层策略可以直接越层穿透到组织后置，彻底跳过中间的用户插件。
  • 等模型思考时停表，报错默认放行。每个插件自身代码只有短暂执行预算，一旦向下层交出控制权或发起模型等待就立刻停表，绝不因为模型想得久误杀插件。普通插件超时或报错一律 fail-open 放行跳过，只有安全门卫才执行 fail-closed 拦截。

把压缩计算藏进人类的空闲间隙（54 分钟窗口）

第二类矛盾来自小时级上下文膨胀与过期悬崖。聊上一小时撞到窗口红线，当场停下来压缩摘要会让终端干等三十秒；如果开发者中间去开四五十分钟会回来，服务端 1 小时缓存马上过期，下一句晚到几分钟就得按无缓存价全量重算。

  • 受控写入通道保底崩溃恢复。所有要重放的状态经由有限的十几个明确写入通道落盘，带清来源标签，崩溃重启也能还原现场。
  • 赶在第 54 分钟提前偷跑摘要。引擎在后台盯住无操作时长，赶在 1 小时缓存到期前的第 54 分钟窗口，趁缓存还热乎悄悄把摘要算好藏在后台先不动当前对话；等容量真撞线或用户开完会回来时，只要主干未偏离锚点，直接毫秒级切换上去，抹平三十秒卡顿也躲开重算悬崖。

第 2 小时以后：模型说完就停机，/loop 如何打通长时值守

前三关全部闯过，但只要退后一步看，这台精密机器本质上依然是个被动应答器：只要某一步模型自认完工、不再调用工具，循环就立刻停回原点等人类敲回车。全库翻五十个文件会把主窗口塞满废纸，盯灰度或跑完整套测试更是没法让人守在屏幕前当人肉触发器。

空间分身：给探索噪声一张单独桌子

面对全库大搜或可拆分的并行改造，主循环按受控并发数与深度上限拉出分身树（Subagent 与队友分身）。每个分身自带一张干净桌子，把翻代码踩坑的几十页日志全关在分支沙盒里，最后只递回几行结论，靠清晰的状态机流转生命周期。

时间接力：为了打破“闭嘴就结束”试过三代写法

  1. 第一代：拿退出门禁硬打回（Stop 拦截）。在出口挂接测试脚本做客观裁决，没绿就驳回退出并注入报错重改。一旦验证脚本写坏就会死磕到底，于是引擎赶紧加上连续打回次数硬熔断（默认连拦 8 次强制断开告警）。
  2. 第二代：固定节拍时钟（固定 Cron）。把唤醒交给会话定时器，调度状态跨压缩保留，终端把连续“一切正常”的空转折叠成单行防止刷屏。但它太机械，既不知风险高低，也容易在后台跑着子任务时叠加无意义轮询。
  3. 第三代：像真人值班一样的自调节 /loop。让模型自己估算下次醒来间隔，并打磨死三个时间耦合：单次睡眠上限卡在 1 小时缓存线前先醒一次保鲜；后台已有任务通知时绝不重复轮询；不再预约闹钟即默契收敛结束，且像 tmux 一样分清“暂时分离界面（detach）”和“彻底取消任务（cancel）”。
演化步点 当初撞上的现实故障 逼出的架构关键设计 跨越的时间尺度难题

还没到终点：下一站是脱离单机进程的持久化

哪怕演进到自调节 /loop，只要唤醒闹钟还挂在单机进程或容器内存里，笔记本盖上休眠、客户端更新重启、系统低内存杀进程或者云端容器销毁，都能把一个跑了三小时的值守循环无声掐断。下一站的方向已经很清晰：让调度意图与现场状态可靠落盘，脱离单机线程，长成跨越进程重启与云容器生命周期的持久化后台运行时。

放到行业坐标系里看：铁轨、黑板作坊，还是隐式内核？

把视线从纵向时间轴拉平，放到今天的整个行业里做个横向比较。大家都在解“怎样让二十行 while 扛住复杂真实工程”这道题，但业界主流押注了三条完全不同的路径：

架构流派 控制权交给了谁 如何管住状态与成本 多方扩展与协同方式 最顺手的场景 绕不开的固有代价
朴素 ReAct 原型 全部交给单线 while 自由拼接 历史全量重传，前缀极易击穿 平级回调硬写，缺乏边界 一次性小脚本、快修单文件 跑长必乱序，账单和延迟失控
显式 Workflow 状态机（DAG 编排） 开发者预先把路修成铁轨 按图节点变量显式流转状态 权限按图节点静态切死 强审计 SOP、步骤固定的企业流 模型遇到意外分支很僵硬，图大了极难维护
多角色黑板协作（如 Swarm 团队制） 平级角色围绕公共黑板与门铃分工 独立窗口隔离碎纸片，黑板对齐结论 组织学隔离（协调者不写代码、独立验收） 大型跨模块并发、破除自写自测偏见 小修小补太沉，跨角色沟通有信息损耗
Claude Code 隐式治理核 + 驻留 Loop 对话表面还是聊天，护栏全沉进随身内核 分层前缀防火墙、工具冻结、54m 预压缩 五层洋葱夹心、越层穿透与停表预算 单开发者面对大仓库从秒级到跨天值守 运行时黑盒重，热插拔不即时生效，持久层债务重

选择做隐式内核，上手几乎零门槛，但你必须清楚它付出的三笔硬账：

  • 热插拔的即时感让位给了缓存稳定。因为前缀与工具清单被线程周期锁死，半路新连进来的能力不能指望立刻生效，必须忍耐到压缩或重启边界。
  • 黑盒越聪明，扩展作者越难排查。五级权限漏斗、安全越层跳过、停表计时与后台预计算都在幕后静默完成，一旦插件没按预期触发，排查链路远不如状态图透明。
  • 把长时值守揽进命令行，就得背上调度系统的持久层重担。一旦鼓励大家用 /loop 挂着盯半天，热更新、休眠唤醒与容器漂移就都变成了必须死磕的基础设施硬骨头。

落到平时怎么选

看透了这四步演进和行业位置，回到日常写代码本身，Claude Code 内部的五种 Loop 形态各自该在什么时候掏出来也就一目了然：

架构形态 核心驱动力 解决的主要矛盾 适合的场景 架构边界
单 Turn 工具循环 模型推理与批次屏障 并发工具执行与消息配对乱序 目标明确、可立即验证的改码与修错 回复结束即停止，无法跨时间等待外部状态

门禁打回循环 Stop 拦截与外部验收器 模型过早宣布完成、主观放水 写完自动跑测试，不过即迭代返工 依赖客观可验证门禁，并受连续拦截熔断限制
