拆解 Claude Code 的 Loop

多 Agent 解决的是空间分工，Loop 解决的是时间连续性：怎样让一个习惯“答完一句就停笔”的模型，把没干完的硬活推进到底，或者自己守着外部状态直到事情落地。

上一篇聊多 Agent 协作时，我们看的是怎么在空间上拆桌子：一个窗口装不下几十个文件的检索噪声，或者自己写代码自己审容易放水，就多请几个独立上下文的角色分头干。

但在日常重度使用编程 Agent 时，还有另一半痛点是靠“多请几个人”解决不了的。它出在时间维度上：默认情况下，Agent 说完一句话就下班了。

Loop 模式是什么，在解什么问题？

所有编程 Agent 的底座，都是单回合（Turn）里的工具循环：你敲下回车，模型想一步，决定调 Read、Edit 或 Bash，拿到输出再想下一步。只要模型还在调工具，这个小循环就会一直转下去。

问题在于，决定它什么时候停下来的，是模型自己的主观判断。一旦某一步它觉得这轮交代完了，不再返回工具调用，当前回合立刻结束，光标退回终端左下角等你敲下一次回车。

修一个报错明确的小 Bug，这种“问一句、跑一轮”的节奏刚刚好。可一旦任务拉长，它马上会在两类场景里卡壳：

第一类是活没干透就早退。比如全库替换一套废弃接口、修掉三十几个连环类型错误，或者把单测补到全绿。模型干了七八步，上下文稍微变长就开始惜力，明明还有测试飘红，它却总结一句“核心逻辑已修改完成，其余文件可按相同方式处理”，然后直接停机。人只能坐在屏幕前当监工，一遍遍敲“继续”“测试还没过，接着修”。

第二类是事不在手边，得等时间走。代码推上去之后，远端 CI 构建要跑十五分钟；线上灰度刚切了 5% 流量，得盯一小时错误率才能决定要不要继续放量。此时本地没有能立刻执行的工具，单轮循环跨不过这段空白时间，总不能让模型在命令行里挂一个 sleep 600 占着连接等超时。

所谓 Loop 模式，就是把“什么时候继续、什么时候停下”的控制权从单次问答里抽出来。不再把模型某一次停笔当成终点，而是在外层套上跨回合的推进机制：要么用客观验证结果逼着它一轮接一轮返工，直到真正达标；要么让会话学会休眠与按时自唤醒，隔一段时间起来看一眼外部状态，直到事情办妥。

Claude Code 具体是怎么做的？

围绕“本地死磕收敛”与“跨时间值守”这两件事，Claude Code 没有去搭复杂的图形化工作流，而是在终端会话里顺着实际需求长出了几层机制。

最底层还是单轮循环配 Subagent。日常大部分短任务，单轮工具循环就能搞定；如果中途要翻几十个文件、怕把主窗口塞满废料，主循环会临时派生出带独立上下文的 Subagent 去查，最后只收几行结论。但这只解决了单轮内的上下文降噪，主模型一停笔，会话照样停。真正跨出单轮边界，靠的是后面三招。

用出口门禁治早退：Stop Hook 与 /ralph-loop

对付模型半途交差，社区最早流行过一种简单粗暴的做法，叫 Ralph Wiggum 模式：直接在终端外面套一层 Bash 死循环 while true，把同一份任务说明反复喂给 Claude，让它每轮看着磁盘上刚改过的代码和 Git 记录接着往下写。

Claude Code 把这个思路收进了会话内部，抓手是 Stop Hook（退出钩子） 和官方的 ralph-loop 插件。

每当模型不再调工具、准备结束当前回合时，Stop 钩子会在出口先拦一道。你可以在这里挂一段真实的测试或编译脚本，也可以挂个轻量模型核对结果。只要验证没过，钩子直接拦下退出动作，把报错日志塞回对话，逼它在当前会话里接着改下一轮。

/ralph-loop 则把它包成了一条现成命令：

/ralph-loop "迁移全部旧版鉴权接口并跑通单测，完成后输出 <promise>DONE</promise>" \
  --completion-promise "DONE" --max-iterations 30

只要模型还没吐出约定的完成标记，钩子就会在每次回合结束时自动把目标重新喂回去。因为全程留在同一条会话和工作区里，模型看得到上一轮改坏了哪行、哪条测试刚变绿，相当于把“模型觉得做完了”改成了“外部验证说过了才算完”。

用固定时钟跨过等待：/loop 5m（Cron 模式）

Stop 钩子是不停歇地连轴转，适合手头一直有代码可改的任务。拿它去等远端 CI 或盯线上服务，只会每秒发请求空烧额度。

为了跨过等待期，Claude Code 加入了会话级定时唤醒，比如直接敲 /loop 5m check the deploy（底层对应周期性的 CronCreate）。这一轮查完发现构建还在跑，回合正常结束并进入休眠，等待期间零算力、零 Token 消耗；5 分钟到点，系统自动往会话里投递下一轮指令。

考虑到长时巡检容易刷屏，如果连续几轮醒来都没发现异常，终端会自动把多次无事可做的空转折叠成一行提示；就算中途对话变长触发了上下文压缩，挂着的定时任务也会保留下来。

把闹钟交给模型自己拧：自调节 /loop（/proactive）

固定间隔 Cron 用起来还是偏死板：刚发版最危险的前五分钟，5 分钟看一次嫌慢；等跑稳了半小时，每 5 分钟醒一次又纯属陪跑；而且机械闹钟自己不知道什么时候该停，非得人来手动关。

于是 /loop 又加了一档不写死间隔的自调节模式（别名 /proactive，底层由模型调用单次唤醒工具 ScheduleWakeup）。每一轮结束前，由模型根据现场风险自己决定下次睡多久再醒：

  • 刚切上灰度流量时风险高，看完首轮指标自己定 2 分钟后再看；
  • 连看几轮指标平稳，主动把间隔拉长到 15 分钟、40 分钟；
  • 等全量发布完成、指标彻底稳住，最后一轮汇报完不再调 ScheduleWakeup 预约新闹钟，整个 Loop 就自然结束收工。

用起来有哪些坑？

循环一旦自动跑起来，小毛病也会跟着循环次数放大。实际在 Claude Code 里用这些能力，有五个坑最常见：

1. 目标没法客观判定，或者门禁脚本自身有 Bug，直接死循环烧额度。
跑 /ralph-loop 时最忌讳写“把代码重构得更优雅”这种主观要求：模型要么第一轮改两行就交差，要么永远停不下来。更常见的是 Stop 钩子里的脚本自己写坏了（比如路径含空格没加引号、测试库连不上，或者把接口报错当成未完成又塞回给模型），导致它在原地白白空转。所以用 /ralph-loop 一定要加 --max-iterations 封顶；Claude Code 后来也专门给 Stop 钩子加了连续拦截 8 次强制熔断，并在 /usage 里拆出了按每个 Loop 单独统计的运行次数与每次 Token 消耗，方便抓出异常空转。

2. 休眠间隔跨过 1 小时，Prompt Cache 全废导致账单暴涨。
跑了十几轮的会话，上下文往往攒了几万到十几万 Token。平时每次唤醒又快又省钱，靠的是服务端默认 1 小时有效期的 Prompt Cache（命中缓存只算零头）。如果你把固定轮询设成 65m，每次醒来缓存恰好过期，十几万 Token 就得每小时按全价重读一遍。这也是为什么自调节 /loop 专门把单次最长睡眠卡死在 1 小时缓存过期线以内：就算模型想等两小时，也会在 1 小时到期前先醒一次把缓存续热。自己设固定间隔时，同样要避开略大于 1 小时的档位。

3. 拿 /loop 去轮询本来就会主动回调的本地后台任务。
不少人在会话里起了个本地后台编译、长测试或后台 Subagent，顺手又敲一个 /loop 1m 看看跑完没。其实 Claude Code 内部拉起的后台任务跑完时，自带 task-notification 主动唤醒主会话，根本不用闹钟催；叠一层轮询只会每分钟往上下文里塞一句“还在跑”的废话。记住一条界线就行：会话内部派出去的慢活靠完成回调唤醒，不会主动通知你的外部系统（远端 CI、线上监控、外部工单）才用 /loop。

4. 无人值守撞上权限确认卡死，以及搞混“脱离界面”和“取消闹钟”。
挂上 /loop 离开座位，结果跑到第 3 轮触发了一个未授权命令或声明了工具权限的 Skill，终端停在“是否允许执行”的弹窗上干等一夜。跑无人值守前，得先把要用的命令或 Skill(name) 配进 permissions.allow 白名单。另外要注意退场按键的区别：连进后台会话看进度时，连按两次 Ctrl+C 只是从当前界面脱离（detach），/loop 还在后台接着跑；按 Esc 才是真正取消待触发的闹钟。

5. 以为关掉终端或合上电脑它还在跑。
目前的 /loop 归根结底是跟着当前会话进程或云端临时容器活的定时器。虽然客户端在热更新或低内存时会尽量保住等待唤醒的后台会话，但只要合上笔记本休眠、杀掉终端进程，或者云端会话容器到期回收，闹钟就会跟着停掉。盯几小时的开发发布很合适，跨天、关机也要跑的任务还是得交给独立的服务端调度。

平时怎么选？

真落到日常干活，不用记内部细节，顺着三个问题就能选定：

  1. 一轮之内能不能搞定？ 改几个文件、马上能跑命令验证的需求，直接走默认单轮循环；嫌查代码太吵或想多路并行改，派几个 Subagent 隔开上下文就行，不用套跨回合 Loop。
  2. 是在死磕本地确定性目标，还是在等外部世界？ 代码和测试都在本地、只是怕模型半路偷懒早退，上 Stop Hook 或 /ralph-loop，绑好验证脚本和轮数上限一口气拱完；如果只是本地起了个十分钟的大编译，丢进后台任务等完成回调叫醒即可。
  3. 等外部状态时，节奏要不要随风险变？ 固定频率例行看一眼，用固定间隔 /loop 10m；盯发版、看灰度、等慢流水线这种前期紧后期松、完事就下班的活，交给自调节 /loop。

把上一篇的多 Agent 和这一篇的 Loop 放在一起，刚好是眼下用好编程 Agent 的一横一纵：多 Agent 在空间上分桌子，防的是上下文被杂事塞乱；Loop 在时间上做接力，治的是模型“答完一句就停笔”的被动性。用法本身并不复杂，真正要守住的只有两条底线：凡是不让它停的循环，出口一定要栓上客观验证脚本和轮数上限；凡是睡过去再醒来的循环，心里一定要算清 1 小时缓存寿命和进程存活边界。
